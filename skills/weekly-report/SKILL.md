# 周报与项目状态报告

把杂乱输入整理成管理层能 30 秒读完的状态报告。

## 3P 结构

- **Progress 进展**：本周完成了什么。只写结果不写过程（"完成 X 模块联调，缺陷收敛到 2 个"，不是"开了三次会讨论 X"）。每条尽量带量化。
- **Plans 计划**：下周做什么，与上周计划对照（完成/顺延/新增，顺延必须给原因）。
- **Problems 问题**：风险与阻塞。每条问题必须带**要谁做什么决定/给什么资源**——没有问题就写"无"，不要凑数。

## 流程

1. **收集素材**：向用户要本周的工作痕迹——git log、聊天记录、会议纪要、邮件、口头列举都行。素材是文件时用对应 skill 提取。用户只给口头描述时，按 3P 追问补全，**特别是 Problems**（人倾向于不报问题）。
2. **归类去重**：把素材映射到 3P；同一件事的多条记录合并；与上周报告对照（用户能提供时）标注延续项。
3. **量化与措辞**：进展条目补数字（完成度%、缺陷数、里程碑日期）；删除"基本""大概""差不多"——不确定的就写明确的不确定（"预计 9/26 完成，依赖供应商到货"）。
4. **输出**：默认 Markdown。要正式交付时用 docx-processing 生成（先问有无公司模板/上周格式，格式延续比美观重要）。

## 分层裁剪

- **给直属领导**：3P 全量 + 技术细节
- **给部门/高管**：只留里程碑级进展、需要决策的问题；一页以内
- 用户没说受众就问一句，两种篇幅差异很大。

## 守则

- 不美化：延期的计划就写延期 + 原因，问题就写问题。报告的信誉来自如实。
- 不虚构：素材里没有的量化数字，宁可空着并向用户要，不要编。
