# 测试驱动开发 / 单元测试生成

TDD 是 红 → 绿 循环。本 skill 让这个循环产出**值得保留**的测试。

## 什么是好测试

测试通过公共接口验证行为，不碰实现细节。好测试读起来像规格说明——"有效购物车可以完成结账"说清了存在什么能力，且内部重构不会弄坏它。

**好**（通过接口验证行为）：
```typescript
test("创建后的用户可以被取回", async () => {
  const user = await createUser({ name: "Alice" });
  expect((await getUser(user.id)).name).toBe("Alice");
});
```

**坏**（绕过接口直查数据库）：
```typescript
test("createUser 会保存到数据库", async () => {
  await createUser({ name: "Alice" });
  expect(await db.query("SELECT * FROM users WHERE name='Alice'")).toBeDefined();
});
```

## Seam：测试放在哪

**Seam** 是你观察行为而不伸手进内部的公共边界。测试只放在 seam 上，永不测内部。

**先约定再动笔**：写任何测试前，列出被测 seam 并与用户确认。没确认的 seam 不写测试。测试不可能覆盖一切，事先约定才能让测试投入落在关键路径上。问用户："公共接口是什么？测哪几个 seam？"

## 反模式（写测试时对照自查）

- **耦合实现**：mock 内部协作者、测私有方法、断言调用次数/顺序。特征：重构没改行为但测试坏了。
- **同义反复**：断言用与被测代码相同的方式重算期望值（`expect(add(a,b)).toBe(a+b)`），构造上必过。期望值必须来自独立事实源：已知正确的字面量、手算样例、规格。
- **水平切片**：先写完全部测试再写全部实现——验证的是想象出来的行为。按**垂直切片**走：一个测试 → 一个实现 → 下一个。

## 循环规则

1. **先红后绿**：先写失败的测试，再写恰好让它通过的最少代码。不预写未来的测试，不加投机功能。
2. **一次一片**：一个 seam、一个测试、一个最小实现。
3. **重构不在循环里**：红绿循环只做行为；重构放评审阶段。

## Mock 准则

- 只 mock **跨进程/跨网络/时钟/随机数** 这类不可控边界；同进程协作者用真的。
- mock 的行为设定必须来自真实契约（文档、录制的响应），不是照实现抄。
- 需要 mock 一切才能测的"单元测试"，通常说明被测对象职责过重——先报告设计问题。

## 为存量代码补测试

1. 先跑通现有测试确认基线绿色；
2. 从用户点名的高风险路径开始，一次一个 seam；
3. 遇到测不动的代码（全局状态、隐藏依赖），先做最小重构开出 seam，再测——重构前后行为用同一组样例输入输出锁定。
