# 日志与故障诊断

疑难 bug 的诊断纪律。只有明确理由才允许跳过阶段。

## 脱敏（贯穿全程）

展示命令、输出、日志片段前，**先把所有密钥/令牌/连接串替换为 `<REDACTED>`**。引用日志只摘携带信号的几行，不整段转贴。

## 阶段 1：建立反馈回路

**这是本 skill 的核心。**有一个对这个 bug 会变红的紧凑通过/失败信号，原因就找得到；没有，盯代码看到天黑也没用。在这一步花不成比例的力气。

按序尝试构造回路：
1. **失败的测试**（单元/集成/e2e，够得着 bug 的那层）
2. **curl/HTTP 脚本**打运行中的服务
3. **CLI 调用** + 固定输入，diff 已知正确的输出
4. **重放捕获的现场**：真实请求/载荷/事件日志存盘，隔离重放
5. **临时 harness**：拉起最小子系统 + 单函数调用复现
6. **二分 harness**：bug 出现在两个已知状态之间时，自动化"状态 X 启动→检查"，配合 `git bisect run`
7. **差分回路**：同一输入跑旧版 vs 新版（或两套配置），diff 输出

### 收紧回路
有了回路还要**收紧**：更快（缓存初始化、缩小范围）、信号更锐（断言具体症状而非"没崩"）、更确定（固定时间、播种随机数、隔离文件系统）。30 秒且时好时坏的回路约等于没有；2 秒且确定的回路是超能力。

### 偶发 bug
目标不是完美复现而是**提高复现率**：循环触发 100 次、并行加压、注入 sleep 收窄时序窗口。50% 复现率可调试，1% 不行——持续拉高到可调试为止。

### 确实建不起回路时
明说建不起，列出尝试过的手段，向用户要：(a) 能复现的环境访问；(b) 脱敏后的现场物料（日志转储、抓包、带时间戳的录屏）；(c) 加临时插桩的许可。**没有回路不进入假设阶段。**

**完成判据**：能报出一条已经跑过的命令，它对这个 bug 稳定变红。

## 阶段 2：二分定位
在回路上做减法：注释掉一半可疑路径 / `git bisect` / 换一半输入数据，每步都跑回路。记录每步结果——二分历史就是最终的根因报告素材。

## 阶段 3：假设与验证
基于二分结果提**一个**最可能的根因假设，用回路验证（改动 → 变绿）。一次只验一个假设；验证失败回到阶段 2，不要连续堆假设。

## 阶段 4：修复与锁定
1. 修复根因（不是症状）；
2. 把阶段 1 的失败回路**保留为回归测试**；
3. 报告格式：症状 → 回路 → 二分路径 → 根因 → 修复 → 回归测试位置。

## 工程现场日志（非代码类故障）
对设备/产线日志：先按时间轴对齐多源日志（控制器、上位机、网络），找**第一个**异常而非最显眼的异常——后面的报错多是级联。把"第一个异常 ± 30 秒"作为回路窗口收窄分析。
