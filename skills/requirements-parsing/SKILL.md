# 需求解析

把杂乱的需求输入变成可评审、可追溯的结构化需求基线。**不发明需求**：每一条都必须能指回原文；推断出来的内容一律标记为假设。

## 流程

### 1. 收集输入
向用户要全部原始材料（文档、邮件、纪要）。材料是文件时用对应文档 skill（pdf/docx/xlsx-processing）先提取文本。记录每份材料的来源与日期。

### 2. 逐条提取
对每条需求产出：

| 字段 | 说明 |
|---|---|
| ID | `REQ-001` 起，稳定不复用 |
| 描述 | 一句"主语 + 必须/应当 + 行为 + 对象"，量化优先（"响应时间 ≤ 2s"而非"要快"） |
| 类型 | 功能 / 性能 / 接口 / 约束（法规、标准、环境）/ 质量属性 |
| 来源 | 指回原文（文件名 + 页码/段落，或"会议纪要 2026-09-22 张工发言"） |
| 验收判据 | 怎样算满足；写不出判据的需求标记为"待澄清" |
| 优先级 | 用户未说明时留空并列入未决问题，不擅自排序 |

### 3. 标注三类问题
- **假设**：原文没写、你为让需求成立而补的前提——全部列出，请用户确认
- **冲突**：两条需求或需求与标准/现状矛盾——成对列出原文
- **未决问题**：含糊、缺失、无法验收的点——写成可以直接转发给需求方的具体问题

### 4. 输出
默认输出 Markdown 表格 + 三个问题清单。用户要交付文档时用 docx-processing 生成正式需求规格（有公司模板先要模板）。

## 守则

- 需求描述禁止出现"等""诸如此类""可能"这类开放措辞——发现了就列进未决问题。
- 不做技术方案：需求解析只回答"要什么"，"怎么做"留给设计阶段。
- 数量大时（>50 条）先给用户分类框架确认，再逐类填充。
